# UltiTools-API 6.3.1 更新说明

6.3.1 替换了框架的 UltiCloud 客户端：通过 UltiCloud 协议 2.1.0 连接 `wss://api.ultikits.com/v1/agent`，
并用设备码接入服务器。面向模块作者的完整清单见
[COMPATIBILITY.md](https://github.com/UltiKits/UltiTools-Reborn/blob/v6.3.1/COMPATIBILITY.md)，
发布页见 [GitHub 上的 v6.3.1](https://github.com/UltiKits/UltiTools-Reborn/releases/tag/v6.3.1)。

::: warning 升级后才能重新连接
自 2026-11-06 UltiCloud 后端切换起，新网关拒绝 6.3.0 的服务器（HTTP 426）。6.3.0 服务器在升级到 6.3.1
之前，无法重新连接面板、执行 `/ulticloud login`、使用 `/panel` 链接或检查模块目录。
:::

## 升级前准备

- 首次启动后，重新执行 `/ulticloud login`。6.3.1 会从 `.ultikits/credentials.json` 中删除 6.3.0 的
  `cloud_token` 并记一条 WARNING，同时保留服务器 `uuid`，面板因此可以提供重新绑定原有服务器的选项。
- 接入改用设备码。控制台会打印网址和有效期 10 分钟的 `XXXX-XXXX` 码，在面板中确认即可。凭据保存在
  `.ultikits/credentials.json`，不会过期。详见[云端登录](/zh/guide/advanced/cloud-login)。
- UltiLogin 的 `/panel` 需要 UltiLogin 2.1.0。UltiLogin 2.0.0 的 `/panel` 在 6.3.1 上不再可用，
  它的 `/login` 仍然可用。
- 直接使用 XSeries 的模块，需要检查 XSeries 14 移除的 API 并重新编译。
- 首次启动时，已有的 6.3.0 `config.yml` 会一次性加入两个新开关 `ultipanel.capabilities.power-actions` 和
  `player-actions`，带注释，值为 `false`。只插入缺少的键，并经过配置写入闸门；你写过的每个字节都保持不变。
- 如果写入闸门无法保留文件的布局，文件不会被写入，两个开关保持关闭，每次启动都会记一条 WARNING 说明键名和原因，
  直到你修正布局或自己加上这两个键。

## 变更

- 替换 UltiCloud 客户端：协议 2.1.0（`wss://api.ultikits.com/v1/agent`），目录 REST 1.1.0
  （`/v1/catalogue/*`）。新增 `/ulticloud reconnect`，`/ulticloud status` 会显示服务器名称。
  详见[面板集成](/zh/guide/advanced/panel-integration#ulticloud-协议-2-1-0)。
- `SensitiveCommandRegistry` 让模块把带密码类参数的命令的参数排除在发往 UltiCloud 的所有内容之外
  （见[敏感命令](/zh/guide/advanced/panel-integration#敏感命令)）。
- `CloudPlayerLinks` 创建一次性玩家链接，取代魔法链接（见[玩家链接](/zh/guide/advanced/player-link)）。
- XSeries 从 13.7.1 升级到 14.0.0，HikariCP 升级到 7，jackson-databind 升级到 2.22.3，log4j 升级到 2.25.4。

## 修复

- 服务器文件操作保护的文件与面板的受保护列表一致。
- 被服务的快照请求会写入审计。

## 弃用

6.3.0 中仅为旧云端服务的公开成员，全部在 6.3.1 弃用，并已在 [6.4.0](/zh/guide/release-notes/6.4.0) 移除。它们在 6.3.1 中要么明确拒绝，要么保持原有行为。
本版本不移除任何公开 API。

## 破坏性变更

没有二进制层面的破坏。针对 6.3.0 编译的模块仍能链接，因为 `PanelResponderRegistry.registerResponder` 与
`dispatch` 擦除后的方法描述符没有变化（已对照 6.3.0 与 6.3.1 的源码核对）。云端功能的运行时行为没有过渡期，
因为之前的云端服务在切换时已经停止。

面板 responder API 有两处源码层面的破坏，用到它们的模块需要先改源码才能针对 6.3.1 重新编译：

| 成员 | 6.3.0 | 6.3.1 | 模块作者要改什么 |
|---|---|---|---|
| `registerResponder(String, Function, String)` 与 `registerResponder(String, Function, String, UltiToolsPlugin)` 的 `responder` 参数 | `Function<JsonObject, CompletableFuture<JsonObject>>` | `Function<JsonObject, ? extends CompletableFuture<? extends JsonElement>>` | lambda 或方法引用仍能编译。覆写这两个方法的子类，需要把参数类型改成新类型。 |
| `dispatch(String, JsonObject, String)` 的返回类型 | `CompletableFuture<JsonObject>` | `CompletableFuture<JsonElement>` | 把接收结果的 `CompletableFuture<JsonObject>` 变量改成 `CompletableFuture<JsonElement>`，或对结果做类型转换。 |

新增的带第四个 `Runnable` 参数的 `dispatch` 重载是新增项，不是破坏。新的约定见
[拥有一个请求/响应类型](/zh/guide/advanced/panel-integration#拥有一个请求-响应类型-panelresponderregistry)。
