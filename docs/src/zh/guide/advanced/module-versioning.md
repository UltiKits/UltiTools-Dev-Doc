# 模块版本规范

这一页讲的是**你的模块**自己的版本号。它不是 `UltiTools-API` 的版本号规则——
框架走的是另一套契约，原因见[为什么模块和框架不一样](#为什么模块和框架不一样)。

## 判据只有一个问题

> **服主换上新 JAR 之后，需不需要动手？**

下面所有规则都是从这一句推出来的。

| | 含义 | 服主要做什么 |
|---|---|---|
| **MAJOR** | 升级需要人工介入 | 手改配置 · 迁移数据 · 重新适应被删除或改名的命令、权限节点 · **先把 UltiTools 本身升级掉** |
| **MINOR** | 新增功能，向后兼容 | 直接换 JAR。旧配置继续工作；新功能可能需要在配置里开 |
| **PATCH** | 修复与内部改动，含纯 CI／构建配置改动 | 直接换 JAR，什么都不用做 |

判据写成「要做多少事」而不是「改动有多大」，是因为两者并不相关。把模块内部
整个重写，只要配置文件和命令没变，那就是 PATCH；改一个权限节点的名字只是一行
diff，却是 MAJOR——因为每一台授予过那个节点的服务器，现在都悄悄少了一项权限。

### bump 之前的检查清单

- [ ] 服主的配置文件需要手改吗？→ **MAJOR**
- [ ] 已有的数据需要迁移吗？→ **MAJOR**
- [ ] 有命令或权限节点被删除或改名吗？→ **MAJOR**
- [ ] `plugin.yml` 的 `api-version` 抬高了吗？→ **MAJOR**
- [ ] 四个都否，但有新功能？→ **MINOR**
- [ ] 四个都否，也没新功能？→ **PATCH**

第四条抓的是前三条漏掉的一种情况，因为模块自己什么都没变。抬高 `api-version` 意味着
还在用旧框架的服主没法只换 JAR ——他们得先升级 UltiTools。按上面那个判据，这就是
MAJOR，哪怕这次发布只是一次源码没动的重新构建——而下面「反方向的风险」里的形状二，
逼你发的正是这样一次构建。

## 为什么模块和框架不一样

`UltiTools-API` 的 [`COMPATIBILITY.md`](https://github.com/UltiKits/UltiTools-Reborn/blob/alpha/COMPATIBILITY.md) 写着：它的版本号是**产品阶段信号，不是严格
的 semver 契约**——框架的 MINOR 版本**可以移除** API。

这看起来和上面的规则自相矛盾。它不矛盾，而且在有人试图「统一」两者之前，值得先
把差别搞清楚。

框架的版本号会被**解析和链接**：Maven 拿它挑选构件，已编译的下游插件在运行时链接
它的类。这两件事问的都是兼容性问题，而一个必须回答兼容性问题的数字，不可能同时是
自由的信号。

模块的版本号**也会被机器读**，但只用来**给两个版本排序**，从不用来判断兼容性：

| 消费者 | 它做什么 |
|---|---|
| `PluginManager.hasNewerVersionLoaded` | 同一模块存在两个 JAR 时，比较版本并拒绝加载旧的那个 |
| `PluginManager.unregisterSupersededVersions` | 卸掉被本次加载取代的旧版本 |
| `UpdateManager.checkModuleUpdates` | 拿已加载版本和已发布版本比对，报告「有更新可用」 |

三者都走 `VersionComparatorUtil.compare`，问的都是同一个问题：A 是不是比 B 大。
没有一个会去看这个差异属于 MAJOR、MINOR 还是 PATCH。

也没有任何东西从 Maven 解析一个模块去给另一个模块用：官方模块里，没有一个在 pom 里声明对
兄弟模块的依赖。（以多模块工程构建的模块——`UltiBot` 就是——依赖的是**它自己的**子模块，
那是那次构建内部的事，不是一个模块链接到另一个模块。）所以约束框架版本号的那条「会被链接」
的理由，够不到模块的版本号。如果你把自己的模块发布出去供别人依赖，这条对你就不再成立，
你继承的是框架的问题，不是这一页的问题。

所以界限是：**顺序被机器消费，MAJOR/MINOR/PATCH 的含义不被机器消费。** 这带来一条
硬性要求，其余全部留给人类读者：

::: tip 唯一的机械约束
版本号必须单调递增且保持可比较。从 `1.10.0` 退回 `1.9.0`、或者中途换一套编号方案，
会让框架在存在两个 JAR 时加载错的那个——而且是**静默**的，输的那个只是被拒绝并记
一条警告。
:::

除此之外，版本号的*形状*是说给服主听的一句话，所以它的规则可以和框架不同，而两者
都不算错。

## 对 `UltiTools-API` 的 pin 是构建输入，不是新鲜度指标

模块把框架声明为 `provided`：

```xml
<dependency>
    <groupId>com.ultikits</groupId>
    <artifactId>UltiTools-API</artifactId>
    <version>${ultitools.version}</version>
    <scope>provided</scope>
</dependency>
```

`provided` 的意思是：模块**编译**时用 pin 的那个版本，**运行**时用服务器上实际
装的框架。这个不对称正是关键：

- 针对**旧** API 编译 → 编译器写进字节码的每一个符号在那个版本里都存在，所以模块不会
  *因为「引用了比服务器更新的东西」* 而 `NoSuchMethodError`。但它仍然可能因为别的原因
  拿到同一个异常，见[反方向的风险](#反方向的风险)。
- 针对**新** API 编译 → 可能引用到服务器的框架没有的方法 → 启动时 `NoSuchMethodError`。

第一条要往窄里读。它说的是**静态链接的引用**在一个方向上的情况，不是一条普遍保证：
之后的框架版本仍然可能移除——或者悄悄改掉——模块正在用的东西；而你通过反射够到的东西
从来就不在这条保证之内，因为编译器根本没看见它。

所以 pin 落后于最新正式版**是正常状态，不是等着被修的漂移**。

**只在模块真的开始用新 API 时，才 bump 这个 pin。**

有一件事 pin **不是**，尽管它听起来像：它不是你的运行时地板。这里是两个互相独立的数字，
而且只有一个会被检查。

| 数字 | 决定什么 | 谁在检查 |
|---|---|---|
| `pom.xml` 里的 `UltiTools-API` 版本 | 你的字节码记录**哪一版的描述符** | 没有人。它是 `provided`，不进你的 JAR，框架运行时看不到它 |
| `plugin.yml` 里的 `api-version` | 声明的运行时**下限** | `PluginManager.isUltiToolsVersionCompatible` —— 模块被放行前唯一被查的**框架版本** |

所以抬高 pin **不会**抬高地板。让这两个数字失步，正是一个 JAR 被放行到它其实跑不了的
框架上的原因。

放行时查的不止这一个数：JAR 会先过结构校验，而且当同一个模块已经加载了更新的副本时也会被拒
（`passesCompatibilityGates` 是 `!hasNewerVersionLoaded && isUltiToolsVersionCompatible`）。
但其中只有 `api-version` 与「你能跑在哪个框架上」有关，所以这一页只谈它。

## 反方向的风险

旧 pin 只买到上面那一条保证，别的都没买到。一个自己没改过的模块照样能炸——因为你的
字节码链接到什么，是框架决定的，不是你决定的。

::: warning
绿色构建不是兼容性的证明。它只证明你的**源码**还能编译——而炸掉一个已发布 JAR 的，
是它字节码里记的**描述符**，编译过程从来不会把那个显示给你看。
:::

[JLS 的二进制兼容性一章][jls13]定义了能造成这种后果的全部变更，比下面列的长。
下面这两种是本项目**真实发出去过**的——**是实例，不是穷举。**

### 形状 1 —— 它用到的 API 被移除了

框架的 MINOR 版本**可能移除** API（见 `COMPATIBILITY.md`）。你拿到哪种链接错误取决于
被移除的是什么：移除**类型**给 `NoClassDefFoundError`，移除**方法、构造器或字段**给
`NoSuchMethodError` / `NoSuchFieldError`。第二种不是假设——当前的移除清单里就有一个
构造器，不只是类型。

抬 pin 重编会发生两件事之一，而且不跑一遍你分不出是哪一件：

- **它把移除暴露出来。** 构建失败，于是你在这里就发现了而不是在别人的服务器上，然后
  你从被移除的 API 迁走。
- **它把调用重定向了。** 某个幸存的东西把这次调用吸收掉，构建通过，重编出来的产物就是
  修好的。

两种都不修**你已经发出去的**那个 JAR——它会一直炸到你把重编版发布为止。所以第二种结果
才是危险的那个：绿色构建看起来像「这儿没事」，而事实上修复品正握在你手里，你得知道要
把它发出去。

而绿色构建很容易拿到，因为**这次扫描只看得见你源码真正写出名字的东西。** 凡是你源码
隐式够到的，都可能悄悄重新解析：

- 一个重载把调用吸收了——`m(String)` 没了，`m(Object)` 还在，你没改过的源码就编译到
  幸存的那个上去了。
- 被移除的类型从来没被写下来过——在 `factory.create().run()` 里 `create()` 的返回类型
  是推断出来的，所以把 `create()` 改指向一个替代类型也能干净编译，而旧字节码里引用的
  仍是被删掉的那个。

代价只在你**真的发布**抬高后的 pin 时才落地：针对更新的框架构建可能记下更新的描述符，
那就意味着诚实地把 `api-version` 也抬上去，而那会把所有还在旧框架上的服务器甩掉。所以
抬 pin 是一次好用的**扫描**，是一个糟糕的**修复**：在一次临时构建里 bump 它、看什么编不过、
从那些 API 迁走，然后**单独**决定发布用的 pin 要不要动。

**这个形状的防线是跟着弃用通告走**——读移除清单，在移除真的发出去之前迁走。

### 形状 2 —— 一个成员名字没变，描述符变了

这个更难缠，因为什么都没被移除，也没有可以标弃用的对象。方法的描述符**同时包含参数类型
和返回类型**，所以改动其中任何一个，都会在同一个名字下产生一个不同的符号。

这已经发生过两次，而第二次更有教学价值。

**6.1.1 → 6.2.0（一个 MINOR）。** 移除 Spring 时改了 `UltiToolsPlugin` 上一个**字段的类型**，
于是 Lombok 生成的 `getContext()` 返回类型跟着变了。每一个已经编译好的、调用它的模块都拿到
`NoSuchMethodError`。没有东西被移除、没有东西被弃用，而那次改动的源码读起来就是一次内部清理。
公开字段的类型变了也一样：编译好的 `getfield` 仍然带着旧描述符，失败于 `NoSuchFieldError`。

**6.2.0 → 6.2.1（一个 PATCH）。** 把数据 API 上的 `AbstractDataEntity` 换成
`BaseDataEntity<String>`，改掉了 **5 个类型上共 14 个公开成员**的描述符——`DataOperator`
的 `exist(T)` / `getById` / `insert(T)` / `update(T)`、`Query` 的 `first()`，以及它们的实现类。
零移除、零新增；每一个受影响的成员都保住了自己的名字。

**是 PATCH 这件事才是重点。** 没有哪个版本级别在这里是豁免的：版本策略排期的是**有意为之**
的移除，所以一次非预期的二进制破坏按定义就不在排期内，而 PATCH 并不被排除在外。

`Query.first()` 值得单独点出来，因为一份按 `DataOperator` 组织的清单会把它藏起来：
**一个只写 `.query()….first()` 的模块，一个 `DataOperator` 方法都没调，照样中招。**

#### 这种破坏是双向的

只要一个符号名字不变、描述符变了，两边就都没有对方那一版。同一个模块、同一份源码，
只动了 pin：

| 构建时 pin | 跑在框架 6.2.0 | 跑在框架 6.2.1+ |
|---|---|---|
| 6.2.0 | 正常 | **`NoSuchMethodError`** —— 找 `(AbstractDataEntity)`，已不存在 |
| 6.2.1 | **`NoSuchMethodError`** —— 找 `(BaseDataEntity)`，尚不存在 | 正常 |

所以「针对新框架重编一下」不是一个能让老服务器留在原地的修复。它只是换了哪一边能跑。
两个格子失败的原因相同、方向相反，这正是为什么修法取决于缺失符号写的是**哪一代**类型
——见[怎么读输出](#怎么读输出-两类成因-修法相反)。

#### 它逼你发布什么

只重编是不够的：pin 还停在旧版本时，构建会重新生成**旧**描述符，新产物照旧以完全相同的
方式失败。所以，**只要你保留那个直接调用点**，你就必须**把 pin 抬到带有新描述符的框架版本
并重编**。（下面的路线 3 是这个「只要」的出口。）

而这还只是一半——并且按上面那张表，是没人检查的那一半。重编出来的 JAR 现在记的是**新**
描述符，所以它在**更老**的框架上会抛 `NoSuchMethodError`。如果 `api-version` 原地不动，
老服务器会高高兴兴地放行这个新 JAR，然后在第一次调用时炸掉。**`api-version` 也要抬。**
——而按这一页开头的检查清单，这会让那一版成为 MAJOR。

不过要抬到**产物真正需要**的那个版本，而不是机械地跟着 pin 走。抬 pin 本身并不意味着输出
就需要更新的框架：如果那次重编只是把一次调用重定向到了两个版本里都存在的成员上，或者你
bump pin 纯粹是为了扫描，那字节码可能仍然跑得动旧地板，而移动它会把一次兼容的修复变成一次
毫无必要的 MAJOR 发布。下一节讲的就是怎么查清楚而不是靠猜；**跟着 pin 走是你没查时的保守
兜底**。

### 怎么真的验一下

「这个 JAR 能不能跑在框架 X 上」是个可以回答的问题，而回答它的方式不是重新编译。把你字节码
引用的符号，和那个框架实际声明的东西比一遍：

```bash
# 在 UltiTools-Dev-Doc 的 checkout 里
python3 scripts/symcheck.py 你的模块.jar UltiTools-API-<你声明的地板>.jar
```

退出码 0 表示没有缺失。非零会列出缺了什么，而那个 JAR 会在第一次走到那些调用点时，在那个
框架上失败。

拿**你在 `api-version` 里声明的那个版本**去跑，而不是你 pin 的那个——那是两个不同的问题，
而前者才是你的用户会撞上的那个。

#### 怎么读输出：两类成因，修法相反

先分清是哪一种形状，因为它们要做的事不一样：

- **这个名字整个没有了** —— 一个重载都不剩，或者类本身就不在。那是形状 1，一次移除。
  去看那一版的移除清单，你手上的是一次**源码迁移**，不是重编。
- **同名的符号还在，只是描述符不同。** 那才是形状 2，下面那张表才适用。

对形状 2，看缺失符号里写的是哪一代类型：

| 缺失符号引用的类型 | 说明什么 | 怎么修 |
|---|---|---|
| **新**的（如 `BaseDataEntity`） | 产物比它声明的地板新 | **抬 `api-version`**，pin 本来就是对的 |
| **旧**的（如 `AbstractDataEntity`） | pin 停在老版本没跟上，输出比地板还旧 | **抬 pin 并重编**；抬 `api-version` 没用，而且更错 |

这两者很容易搞反，而修法指向相反的方向，所以值得把符号读一遍，而不是伸手去够那个更顺手的
数字。

脚本没法替你下这个判断：它拿到的是一个模块 JAR 和一个框架 JAR，所以它看得见某个符号不在，
看不见**为什么**，而且它根本看不到你的 pin。**它负责报告，你负责判读。**

还有两件事它会明说而不是猜。凡是继承链走出这两个 JAR 的——比如框架类继承自某个 API JAR
没打包的服务端 API 或 GUI 库——都列为**无法判定**，且不影响退出码，因为把一次合法的继承调用
报成缺失就是假阳性。而如果 `javap` 自己失败了，整次运行直接中止，不会拿残缺输出去分析：
引用变少在下游读起来就是一份「没问题」的报告。

::: tip 为什么用脚本而不是手敲 `javap`
对单个类跑 `javap -s` 确实能回答「这个成员的描述符是什么」，但你手上的问题是「**整个 JAR**
里有没有任何东西引用了那个框架没有的符号」，那是一次跨两个产物的比对。

有一个陷阱会让手工版不可靠：常量池里记的是**调用点的静态接收者类型**，不是声明该成员的类。
在你自己的插件类里调一个继承来的框架方法，记下来的 owner 是**你的**类——
`com/example/MyPlugin.getContext:()…`——所以「只过滤 owner 已经在框架包里的引用」会漏掉
每一个继承调用。而既然插件都继承 `UltiToolsPlugin`，那就是其中的大多数。
:::

### 当两边都必须能跑

不能横跨两边的是**静态链接**的调用点——描述符在编译期就烧进去了，所以一个调用点只匹配一边。
于是剩下三条路线，代价递增：

1. **接受更高的地板**（默认选这条）。老服务器留在老 JAR 上；新的那个服务新框架。
2. **按框架区间发不同的产物**，并维护两条线。
3. **写一层垫片**：改用反射调用（`getMethod("getContext").invoke(plugin)` 返回 `Object`，
   再用同样的方式够到 `getBean`），或者按框架版本懒加载不同的适配器。反射调用点不链接到
   任何一个描述符，所以一个产物真的可以跑在两边。代价是这条路失去了编译期检查——你会在
   运行时才发现问题，而且下次框架再改它的形状时，你连一条构建警告都拿不到。

路线 3 是真的可用；别因为它排在最后就排除它。但它拿构建期的失败换了运行时的失败，所以只有
在你**必须**继续支持老服务器时，它才值那个价。

注意这对「pin 落后是正常状态」意味着什么。那条规则说的是别**没有理由**地动 pin——而描述符
变更就是一个理由，上面那个决定路由回这里的任何情况也都是。

### 如果你的链接错误不是这两种形状

那你撞上的是 JLS 里另外几类之一——把实例方法改成 `static` 给 `IncompatibleClassChangeError`，
收窄成员的可见性给 `IllegalAccessError`，还有更多。用一个问题给自己分流：
**框架是不是移除了什么？**

- **是** → 它应该在移除清单上。如果不在，请开一个 issue；那是一次策略失败，不只是你的问题。
- **否** → 试上面那条重编路径（抬 pin → 重编 → 抬 `api-version`）。如果重编**编译不过**，
  说明那次变更同时破坏了源码兼容性，你手上的是一次迁移而不是一次重编。

[jls13]: https://docs.oracle.com/javase/specs/jls/se21/html/jls-13.html

## 目前各模块的状态

大部分模块还停在 `1.0.0`，因为它们还没有过需要做这个判断的发布。有两个在这一页
存在之前就各自做了判断，而且结论相反——一个用 MINOR 表示 bug 修复，另一个用 MAJOR
表示新功能，都对不上上面那张表。它们会按模块逐个校正口径，而不是回溯改号：已经
发布出去的版本号，服主可能已经记在什么地方了。
