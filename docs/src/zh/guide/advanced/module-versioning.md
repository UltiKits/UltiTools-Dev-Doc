# 模块版本规范

这一页讲的是**你的模块**自己的版本号。它不是 `UltiTools-API` 的版本号规则——
框架走的是另一套契约，原因见[为什么模块和框架不一样](#为什么模块和框架不一样)。

## 判据只有一个问题

> **服主换上新 JAR 之后，需不需要动手？**

下面所有规则都是从这一句推出来的。

| | 含义 | 服主要做什么 |
|---|---|---|
| **MAJOR** | 升级需要人工介入 | 手改配置 · 迁移数据 · 重新适应被删除或改名的命令、权限节点 · **先把 UltiTools 本身升级掉** |
| **MINOR** | 新增功能，向后兼容 | 直接换 JAR。旧配置继续工作；新功能可能需要在配置里开 |
| **PATCH** | 修复与内部改动，含纯 CI／构建配置改动 | 直接换 JAR，什么都不用做 |

判据写成「要做多少事」而不是「改动有多大」，是因为两者并不相关。把模块内部
整个重写，只要配置文件和命令没变，那就是 PATCH；改一个权限节点的名字只是一行
diff，却是 MAJOR——因为每一台授予过那个节点的服务器，现在都悄悄少了一项权限。

### bump 之前的检查清单

- [ ] 服主的配置文件需要手改吗？→ **MAJOR**
- [ ] 已有的数据需要迁移吗？→ **MAJOR**
- [ ] 有命令或权限节点被删除或改名吗？→ **MAJOR**
- [ ] `plugin.yml` 的 `api-version` 抬高了吗？→ **MAJOR**
- [ ] 四个都否，但有新功能？→ **MINOR**
- [ ] 四个都否，也没新功能？→ **PATCH**

第四条抓的是前三条漏掉的一种情况，因为模块自己什么都没变。抬高 `api-version` 意味着
还在用旧框架的服主没法只换 JAR ——他们得先升级 UltiTools。按上面那个判据，这就是
MAJOR，哪怕这次发布只是一次源码没动的重新构建——而下面「反方向的风险」里的形状二，
逼你发的正是这样一次构建。

## 为什么模块和框架不一样

`UltiTools-API` 的 [`COMPATIBILITY.md`](https://github.com/UltiKits/UltiTools-Reborn/blob/alpha/COMPATIBILITY.md) 写着：它的版本号是**产品阶段信号，不是严格
的 semver 契约**——框架的 MINOR 版本**可以移除** API。

这看起来和上面的规则自相矛盾。它不矛盾，而且在有人试图「统一」两者之前，值得先
把差别搞清楚。

框架的版本号会被**解析和链接**：Maven 拿它挑选构件，已编译的下游插件在运行时链接
它的类。这两件事问的都是兼容性问题，而一个必须回答兼容性问题的数字，不可能同时是
自由的信号。

模块的版本号**也会被机器读**，但只用来**给两个版本排序**，从不用来判断兼容性：

| 消费者 | 它做什么 |
|---|---|
| `PluginManager.hasNewerVersionLoaded` | 同一模块存在两个 JAR 时，比较版本并拒绝加载旧的那个 |
| `PluginManager.unregisterSupersededVersions` | 卸掉被本次加载取代的旧版本 |
| `UpdateManager.checkModuleUpdates` | 拿已加载版本和已发布版本比对，报告「有更新可用」 |

三者都走 `VersionComparatorUtil.compare`，问的都是同一个问题：A 是不是比 B 大。
没有一个会去看这个差异属于 MAJOR、MINOR 还是 PATCH。也没有任何东西从 Maven 解析
模块、或链接到模块——模块不发布到 Maven 仓库，模块之间也不互相依赖。

所以界限是：**顺序被机器消费，MAJOR/MINOR/PATCH 的含义不被机器消费。** 这带来一条
硬性要求，其余全部留给人类读者：

::: tip 唯一的机械约束
版本号必须单调递增且保持可比较。从 `1.10.0` 退回 `1.9.0`、或者中途换一套编号方案，
会让框架在存在两个 JAR 时加载错的那个——而且是**静默**的，输的那个只是被拒绝并记
一条警告。
:::

除此之外，版本号的*形状*是说给服主听的一句话，所以它的规则可以和框架不同，而两者
都不算错。

## 对 `UltiTools-API` 的 pin 是构建输入，不是新鲜度指标

模块把框架声明为 `provided`：

```xml
<dependency>
    <groupId>com.ultikits</groupId>
    <artifactId>UltiTools-API</artifactId>
    <version>${ultitools.version}</version>
    <scope>provided</scope>
</dependency>
```

`provided` 的意思是：模块**编译**时用 pin 的那个版本，**运行**时用服务器上实际
装的框架。这个不对称正是关键：

- 针对**旧** API 编译 → 可以证明模块只用了那个版本就有的东西 → 它**不会**因为
  「引用了比服务器更新的 API」而 `NoSuchMethodError`。但它仍然可能因为**别的原因**
  拿到同一个异常，见下方的警告。
- 针对**新** API 编译 → 可能引用到服务器的框架没有的方法 → 启动时 `NoSuchMethodError`。

这是对**一种**失败模式的保证，不是「向前兼容」本身：之后的框架版本仍然可能移除——
或者悄悄改掉——模块正在用的东西。见下方的警告。

所以 pin 落后于最新正式版**是正常状态，不是等着被修的漂移**。

**只在模块真的开始用新 API 时，才 bump 这个 pin。**

有一件事 pin **不是**，尽管它听起来像：它不是你的运行时地板。这里是两个互相独立的数字，
而且只有一个会被检查。

| 数字 | 决定什么 | 谁在检查 |
|---|---|---|
| `pom.xml` 里的 `UltiTools-API` 版本 | 你的字节码记录**哪一版的描述符** | 没有人。它是 `provided`，不进你的 JAR，框架运行时看不到它 |
| `plugin.yml` 里的 `api-version` | 声明的运行时**下限** | `PluginManager.isUltiToolsVersionCompatible` —— 模块被放行前唯一被检查的值 |

所以抬高 pin **不会**抬高地板。让这两个数字失步，正是一个 JAR 被放行到它其实跑不了的
框架上的原因。

::: warning 反方向的风险
旧 pin 只买到上面那一条保证，别的都没买到。有两件事仍然能让一个自己没改过的模块炸掉。

**形状一：它用的 API 被移除了。** 框架的 MINOR 版本**可以移除** API（还是那句，见
`COMPATIBILITY.md`）。报哪个链接错误取决于被移除的是什么：移除**类型**给你
`NoClassDefFoundError`，而移除**方法、构造器或字段**给你 `NoSuchMethodError` /
`NoSuchFieldError`。后一种不是假设——当前的移除清单里就有一个构造器，不只是类型。

把 pin 调到最新**防不住**这件事——不管你针对哪个版本编译，那个类在运行时都已经没了
——但它能把问题**暴露出来**：模块会编译不过，于是你在构建时就发现，而不是在别人的
服务器上。代价只在你真的**发布**那个抬高后的 pin 时才落下来：针对更新的框架构建可能记录
更新的描述符，那就意味着 `api-version` 也得诚实地一起抬，于是丢掉所有还在用旧框架的服务器。
所以调 pin 是一次好用的**排查**、而不是一个**修复**：在一个临时构建里把它调上去，看什么
编译不过，把那些 API 迁移掉，再单独决定正式发布的 pin 要不要跟着动。

**形状二：它调的方法名字没变，描述符变了。** 这一种更难缠，因为没有任何东西被移除，
也就没有可以废弃的对象。它已经发生过：6.1.1 → **6.2.0** 那一版改的是 `UltiToolsPlugin`
上一个**字段的类型**，于是 Lombok 生成的 `getContext()` 的返回类型跟着变了。返回类型是
JVM 方法描述符的一部分，所以所有已经编译好、调用它的模块都拿到 `NoSuchMethodError`。
至于**源码**破没破，取决于你怎么调的：`getContext().getBean(X.class)` 从没写出返回类型
的名字，照样编得过；但把返回值赋给旧类型、或者覆写这个方法，就编不过了。

两种形状的防线不一样。形状一的防线是**跟进废弃通告**——读移除清单，在移除真正发生之前
迁移完。

形状二没有通告可跟，而且**没有免费的修法**。光重新编译不够：pin 还停在旧版本时，构建照着
旧的 class 文件生成的仍是**旧**描述符，新产物照炸。所以必须**把 pin 抬到含新描述符的那个
版本再重编**。

而这还只是一半，并且按上面那张表，是**没人检查的那一半**。重编后的 JAR 记录的是新描述符，
装到**更旧**的框架上会拿到同一个 `NoSuchMethodError`，只是方向反过来。如果 `api-version`
原地不动，老服务器会痛快地放行这个新 JAR，然后在第一次调用时炸掉。**`api-version` 要一起
抬。** 一个构件没法同时服务描述符变更的两侧：要么**接受地板抬高**（老服务器继续留在旧 JAR
上），要么**按框架区间出不同构件**。

这是「pin 落后是正常状态」**唯一不适用**的情况。那条规矩说的是**没有理由时**不要动 pin；
描述符变更就是一个理由。另外，版本号策略排期的是**有意为之**的移除，无意的描述符变更按
定义不在排期里，所以没有哪一级版本对它免疫，PATCH 也不例外。
:::

## 目前各模块的状态

大部分模块还停在 `1.0.0`，因为它们还没有过需要做这个判断的发布。有两个在这一页
存在之前就各自做了判断，而且结论相反——一个用 MINOR 表示 bug 修复，另一个用 MAJOR
表示新功能，都对不上上面那张表。它们会按模块逐个校正口径，而不是回溯改号：已经
发布出去的版本号，服主可能已经记在什么地方了。
